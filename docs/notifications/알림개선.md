# 알림 발행 보장 - 유실 등급을 타입별로 나누고, 보장이 필요한 것만 outbox로

> 작성 2026-09-06. 코드 기준 `content-service` main 브랜치.
> 형식: 상황 -> 무엇이 일어났나 -> 바꾼 것 -> 현재 상태. 안 돌린 실험은 "미측정"으로 적는다.

## 한 줄 요약

알림을 "유실 허용 / 유실 불가" 두 등급으로 나눴다. 전 타입에서 유령 알림은 `AFTER_COMMIT`으로 막았고,
유실 불가 타입에만 Transactional Outbox로 발행을 보장한다. 유실 허용 타입에 outbox를 안 쓴 이유는
비용이 아니라 **보장을 사면 따라오는 중복과 지연이 그 타입에서는 순손실**이기 때문이다.

## 1. 상황

| 항목 | 내용 |
|---|---|
| 서비스 | `content-service` (K3s, 2 replica). 알림은 Kafka `user.notifications`로 발행, `chat-service`가 소비해 Mongo 저장·푸시 |
| 기존 결정 | 2026-07 블로그 문서: "유실은 허용, 유령만 차단. 발행 100% 보장(Outbox)은 과설계" ([docs/blog/event-driven-notification-after-commit.md](../blog/event-driven-notification-after-commit.md)) |
| 실측 | 카오스 IN-2 (Kafka 5분 17초 다운): 알림 유실 **정확히 1건**. 댓글 본문은 MySQL에 저장, 알림만 증발 ([docs/chaos/scenarios/IN-2/answer.md](../chaos/scenarios/IN-2/answer.md)) |
| 질문 | 배틀 종료 알림처럼 사용자가 스스로 알아차릴 수 없는 알림도 "유실 허용"인가 |
| 결과 | 등급 분류·구현 완료(2026-09-06, 테스트 269 통과), 측정은 미착수 (§9) |

## 2. 현행 구조

### 2.1 요청 경로 (댓글·좋아요·아이템 추가)

```
사용자 요청
  -> FeedCommentService 등  @Transactional
       MySQL 저장 + publishEvent(NotificationEvent)        ... 롤백이면 이벤트도 폐기 (유령 차단)
  -> COMMIT
  -> NotificationEventListener  @TransactionalEventListener(AFTER_COMMIT) + @Async
  -> notificationExecutor  (스레드 2~5, 큐 100, CallerRunsPolicy)      [유실 구간 A]
  -> KafkaTemplate.send   (acks=all, retries=3, 멱등, key=userId)      [유실 구간 B]
  -> user.notifications   (6 파티션, 복제 1, 보존 7일)
  -> chat-service -> Mongo user_notifications, 푸시
```

- **유실 구간 A - 커밋 직후 파드 종료.** 이벤트가 메모리 큐에만 있어 파드와 함께 사라진다. 배포 롤링마다 열린다.
- **유실 구간 B - Kafka 접속 불가.** 3회 재시도 후 `log.error` 한 줄. 재시도 큐도 저장도 없다. IN-2의 유실 1건이 여기다.
- DLQ 토픽(`user.notifications.dlq`)은 만들어져 있지만 프로듀서는 쓰지 않는다.
- 알림 1건은 어디에도 기록되지 않으므로 A·B에서 사라진 알림은 다시 보낼 근거가 없다.

### 2.2 스케줄러 경로 (배틀 D-7, 배틀 종료)

```
@Scheduled (종료: 매분 / D-7: 매시)
  -> @SchedulerLock  (Redis, 리더 1대, lockAtMostFor 5m / 10m)
  -> battleRepository.findByEndDateBetween  창 [now-1m, now)  (폭 = 주기)
  -> TB_BATTLE_NOTIFICATION_SENT  (battleId, phase, userId) 유니크 -> 이미 있으면 skip, 없으면 저장
  -> notificationService.notifyBattleResult...  -> publishEvent
  -> (2.1의 COMMIT 이후 경로로 합류)
```

여기서만 "보내기로 결정했다"가 DB에 남는다. 그러나 "실제로 전송됐다"는 남지 않는다.

- **Kafka 전송이 실패해도 sent 행은 커밋된다.** 다음 실행은 그 사용자를 "이미 보냄"으로 취급한다. 재시도 없음.
- **리더가 실행 중 종료되면 락 만료(최대 5분)까지 전원 정지.** 다음 실행의 창은 그때의 `now` 기준 1분이라
  정지 중 종료된 배틀은 어떤 창에도 안 들어간다. **지연이 아니라 누락**이다.

```
12:00:00 실행 시작 (창 [11:59, 12:00))
12:00:30 리더 종료, 락 미해제
12:01 ~ 12:05  다른 파드: 락 획득 실패로 매분 skip
12:05:30 락 만료
12:06:00 다른 파드 실행, 창 [12:05, 12:06)
         -> 12:00 ~ 12:05 사이 종료된 배틀: 어떤 창에도 없음 -> 알림 누락
```

- `TB_BATTLE_NOTIFICATION_SENT`에 삭제·정리 로직이 없다. 배틀 x 수신자 행이 영구 누적.

### 2.3 타입은 열넷, 등급은 하나

전 타입이 같은 경로, 같은 at-most-once다. 사용자가 원본 화면에서 스스로 발견할 수 있는지는 타입마다 다른데,
그 차이가 코드에는 없다.

## 3. 무엇이 일어났나

**발견.** 블로그 문서의 "Outbox는 과설계" 판단을 다시 읽었다. 근거는 비교표의 "비용: 높음" 한 칸이었고,
무엇이 얼마나 비싼지는 없었다. 한편 IN-2에서 유실 1건이 실측돼 있었다.

**첫 판단.** "유실 허용 타입에 outbox를 안 쓴 것은 비용 때문"으로 정당화하려 했다. 그러려면 어디서 비용이
큰지 숫자가 있어야 한다.

**검토.** 이 코드에서 유실 허용 타입에 outbox를 얹을 때 생기는 건당 비용을 어림했다.

| 항목 | 지금 | outbox 적용 시 | 어림 |
|---|---|---|---|
| 좋아요 트랜잭션의 쓰기 | 2회 (reaction 저장, feed 갱신) | 3회 | INSERT 1건 추가. 절대량 작음 |
| 발행 후 | 없음 | published 갱신 1회 + 나중 삭제 1회 | 요청 경로 밖 |
| E2E 알림 지연 | 0.9초 (IN-2 정상 구간 실측) | 폴링 주기 추가 | 1초 폴링이면 약 1.4~1.9초 |
| 소비자 멱등 처리 | 불필요 | 필요 | outbox를 한 타입에라도 넣으면 필요. 타입 추가의 한계비용 0 |
| 테이블 정리 배치 | 없음 | 있음 | 한 번 내면 끝 |

지금 규모에서는 전부 작게 나올 가능성이 높다. **"비용이 커서 안 썼다"는 논리는 숫자 없이는 서지 않고,
숫자를 내도 작게 나오면 무너진다.**

**접근 변경.** outbox의 목적으로 돌아갔다. outbox는 "커밋된 사실이 있으면 그 이벤트는 언젠가 반드시 발행된다"를
만드는 장치다. 그 대가로 **at-least-once(중복 가능)** 와 **폴링 지연**이 확정적으로 따라온다.
보장이 필요 없는 타입에서 이 둘은 얻는 것 없는 순손실이다. 좋아요 알림이 두 번 오는 것은 한 번 안 오는 것보다
사용자에게 더 거슬린다. 그래서 분리 근거를 비용에서 **"보장이 필요한가"** 로 바꿨고, 그 판정 기준을
세 질문으로 고정했다 (§5).

## 4. outbox를 쓰는 이유와 보장의 범위

**이유.** DB 커밋과 Kafka 전송은 원자적으로 묶을 수 없다. 발행 의도를 같은 트랜잭션 안의 행으로 남기면
커밋과 함께 살고 롤백과 함께 죽는다. 릴레이가 그 행을 읽어 보내고 성공 시 표시한다. 파드가 죽어도,
Kafka가 죽어도 행은 남아 있으므로 다시 보낼 근거가 생긴다.

**보장하는 것.** 프로듀서 쪽. 커밋된 이벤트는 Kafka가 살아 있을 때 반드시 브로커 ack까지 도달한다.

**보장하지 않는 것.**

- 브로커 내구성. 토픽이 복제 1이라 브로커 디스크가 죽으면 ack 이후에도 사라질 수 있다. `acks=all`은 복제 2 이상,
  `min.insync.replicas>=2`부터 의미를 갖는다.
- 소비자 처리. `chat-service`가 Mongo에 넣는 과정은 소비자 책임이고, 멱등 처리가 없으면 at-least-once의 중복이
  사용자에게 그대로 노출된다.

정확한 문장은 "outbox를 넣었으니 확실히 온다"가 아니라 **"우리 서비스에서 사라지는 일은 없다. 그 뒤는
브로커 복제와 소비자 멱등이 담당한다"** 다.

## 5. 판단 근거와 등급 분류

세 질문 중 하나라도 "예"면 유실 불가.

| 질문 | 뜻 |
|---|---|
| (1) 시효가 있나 | 특정 시각을 놓치면 알림의 가치가 사라지는가 |
| (2) 대체 경로가 없나 | 알림이 안 와도 사용자가 원본 화면에서 스스로 알아차릴 수 있는가 |
| (3) 타인의 흐름을 막나 | 수신자가 모르면 다른 사용자의 작업이 대기 상태로 남는가 |

### 유실 불가 - outbox로 발행 보장

| 타입 | 진입점 | (1) | (2) | (3) | 근거 |
|---|---|---|---|---|---|
| `BATTLE_RESULT` · `BATTLE_RESULT_WITH_WINNER` | 스케줄러 매분 | 예 | 예 | - | 종료 시각에만 의미. 투표자는 자기가 참여한 배틀의 종료 시각을 기억하지 않음 |
| `BATTLE_DEADLINE_OWNER_D7` | 스케줄러 매시 | 예 | 예 | - | 마감 전 유일한 리마인더 |
| `BATTLE_ITEM_APPROVAL_REQUEST` (+BATCH) | 요청 (아이템 추가, PUBLIC_APPROVAL 배틀) | - | 예 | 예 | 생성자가 승인해야 아이템이 노출됨. 유실 = 요청자 무한 대기 |
| `BATTLE_INVITE` | 호출부 없음 | - | 예 | - | 초대 사실을 알 경로가 없음. 사용 시작 시 불가 등급 |
| `SYSTEM` | 호출부 없음 | - | 예 | - | 운영자 발신. 유실은 운영 사고 |

### 유실 허용 - AFTER_COMMIT 직접 전송 유지

| 타입 | 진입점 | 근거 |
|---|---|---|
| `FEED_COMMENT` · `BATTLE_ITEM_COMMENT` | 요청 (댓글) | 댓글은 피드·아이템 화면에 남아 있음 |
| `FEED_LIKE` · `BATTLE_ITEM_LIKE` | 요청 (반응) | 좋아요 수에 반영. 최다 발생 타입이고 중복 알림이 유실보다 거슬림 |
| `FOLLOW` | 요청 | 팔로워 목록에 보임 |
| `BATTLE_ITEM_ADDED` (+BATCH) | 요청 (아이템 추가, 승인 불필요 배틀) | 아이템이 목록에 바로 노출. 막히는 흐름 없음 |

### 경계

- 아이템 신고 3회 누적 시 생성자 알림(`notifyItemUnderReview`)은 `BattleItemService`에 주석 처리된 호출만 있고 메서드도 타입도 없다. 구현하면 (3)에 해당해 불가 등급.

### 분류가 구조에 주는 것

- 불가 타입 일곱 중 셋(결과 2종, D-7)은 스케줄러 발이고 `TB_BATTLE_NOTIFICATION_SENT`가 이미 있다.
  outbox 유니크 키를 (battleId, phase, userId)로 잡으면 그 행이 dedup 역할을 겸하므로 **테이블이 하나 줄어든다.**
  "보내기로 했다"와 "전송됐다"가 한 행의 상태 전이로 합쳐지고 §2.2의 "실패해도 sent로 남는" 구멍이 구조적으로 사라진다.
- 불가 중 요청 경로에서 나가는 것은 승인 요청 하나다. **요청 트랜잭션에 outbox INSERT가 붙는 곳은 이 한 군데**고,
  좋아요·댓글 같은 최다 발생 경로에는 붙지 않는다.

## 6. 검토한 대안과 기각 사유

| # | 대안 | 기각 사유 (이 코드 기준) |
|---|---|---|
| 1 | 현상 유지 (전 타입 유실 허용) | 근거가 "비용 높음" 한 칸. 배틀 결과는 종료 시각에만 의미가 있어 유실 시 대체 경로 없음 |
| 2 | 트랜잭션 안에서 동기 전송 | 유령 알림 발생. 이것을 고치려고 AFTER_COMMIT으로 옮긴 것이 원래 이력 |
| 3 | 프로듀서 설정 강화 (retries·delivery.timeout 확대, 동기 대기) | 커밋 직후 파드 종료 구간은 메모리 큐(용량 100)라 어떤 설정으로도 못 넘김. Kafka 장애가 timeout보다 길면 동일. 동기 대기는 요청 지연을 Kafka에 결합 |
| 4 | 인메모리 재시도 큐 | 3과 같은 이유. 파드와 함께 사라짐 |
| 5 | Kafka 트랜잭션 프로듀서 | Kafka 내부 원자성만 보장. DB 커밋과 묶이지 않아 이중 쓰기 문제를 해결하지 못함 |
| 6 | sent 테이블에 상태 컬럼만 추가 | 스케줄러 발 3종에는 유효하나 승인 요청은 요청 경로라 그 테이블이 없음. 최종안이 아니라 구현 1단계로만 남김 |
| 7 | 소비자 측 보정 (chat이 종료 배틀을 주기 조회) | 서비스 간 결합과 폴링. 요청 경로 타입은 커버 못 함 |
| 8 | CDC (Debezium) | content 2 replica 규모에 Kafka Connect 클러스터와 RDS binlog ROW 설정 추가. 인프라 예산 제약 |
| 9 | 전 타입 outbox | 기각이 아니라 **보류.** 구조는 같고 등급 값만 다르다. 유실 허용 타입에서는 중복·지연이 순손실이라 기본값을 분리로 두고, §8의 비교 실측 뒤 재결정 |
| 10 | 상태 재도출 (스케줄러가 "종료됐는데 sent 기록 없는 것"을 창 없이 찾고, Kafka ack 뒤에만 기록) | **배틀 3종에는 outbox보다 싸다.** 새 테이블 없이 유실과 리더 종료 누락이 함께 사라진다. 그러나 승인 요청·초대·시스템은 요청 경로라 타입마다 "보내야 할 상태" 조회를 따로 짜야 하고, 불가 타입이 늘 때마다 그 쿼리가 하나씩 는다. 배틀 밖으로 나가는 순간 outbox가 이기고, 승인 요청이 이미 밖에 있다 |

**채택 전제.** outbox는 "불가 타입 일곱을 한 구조로 받는다"는 전제 위에서 최선이다. 목표가 배틀 3종만이라면
대안 10이 맞고, 이 문서의 결론은 뒤집힌다. 전제를 이렇게 둔 이유는 승인 요청이 이미 요청 경로에 있고,
불가 타입이 앞으로 배틀 밖에서 늘어날 것이기 때문이다.

## 7. 바꾼 것

### 7.1 릴레이 방식 선택 - "즉시 전송 + 리더 청소"

outbox까지는 어느 방식이든 같다. 갈리는 것은 PENDING 행을 누가 읽어 Kafka로 보내느냐다. 후보 일곱을 놓고 봤다.

| # | 방식 | 정상 지연 | 폴링 (2대) | 릴레이 장애 시 | 새로 필요한 것 | 판정 |
|---|---|---|---|---|---|---|
| 1 | 전원 폴링 · SKIP LOCKED | 약 1초 | 2회/초 | 나머지가 계속 | 없음 | 리더 방식이 이미 있어 이점 없음 |
| 2 | ShedLock 리더 1대 폴링 | 약 1초 | 1회/초 | 락 만료까지 지연 | 없음 | 지연이 밀리초에서 초로 후퇴 |
| 3 | 샤드별 리더 N대 | 약 1초 | N회/초 | 샤드 하나만 지연 | shard 컬럼 · 락 N | 리더 처리량 병목이 실측되면 |
| **4** | **커밋 직후 즉시 전송 + 리더가 잔여분 청소** | **밀리초** | 1회/30초 | 2와 같음 | 없음 | **채택** |
| 5 | 전용 릴레이 파드 | 약 1초 | 1회/초 | 재기동까지 지연 | Deployment 1 | 릴레이 부하가 앱 응답에 잡히면 |
| 6 | Kafka Connect JDBC Source | 수초 | Connect가 | Connect 재배치 | Connect 클러스터 | Connect 올릴 거면 7 |
| 7 | Debezium CDC | 밀리초 | 없음 | Connect 재배치 | Connect + binlog ROW | 수십 대 규모에서 정석 |

**4를 고른 이유.** 지금 코드가 이미 "커밋 직후 즉시 전송"이다. 그 앞에 outbox INSERT, 뒤에 "ack 오면 SENT"를
붙이고, 이미 있는 ShedLock 리더에게 남은 행 청소를 맡기면 끝난다. 정상 경로 지연은 현행(E2E 0.9초) 그대로이고
폴링은 실패분에만 관여한다. 새 인프라가 없다.

**리더 한 대가 청소를 감당하는 근거.** 릴레이 부하는 "무엇이 outbox에 들어오나"로 정해진다.

| | 들어오나 | 발생량의 성격 |
|---|---|---|
| 좋아요 · 댓글 · 팔로우 · 아이템 추가 | 아니오 (BEST_EFFORT) | 최다 발생 타입. 이 경로를 타지 않는다 |
| 배틀 결과 · D-7 | 예 | 배틀 종료 건수 x 참여자 수. 매분 스케줄러가 만드는 양이 상한 |
| 승인 요청 | 예 | PUBLIC_APPROVAL 배틀의 아이템 추가 요청 건수. 사용자 행동 중 드문 편 |
| 초대 · 시스템 | 예 | 호출부 없음 |

- 평상시 즉시 전송이 성공하면 릴레이가 읽는 결과는 **빈 집합**이다. 폴링 1회는 인덱스 (status, created_at)를
  타는 SELECT 하나이고 30초마다 한 번이다.
- 릴레이가 실제로 일하는 것은 Kafka 장애·파드 종료 뒤 복구 구간뿐이고, 그때 쌓인 양은 "장애 시간 동안의
  GUARANTEED 알림 수"다. 좋아요·댓글이 빠져 있어 이 수가 작다. 리더 한 대가 created_at 순으로 보내면
  같은 사용자 알림 순서도 유지된다.
- 처리량이 병목으로 실측되면 3(샤드)으로 올라간다. 지금은 측정된 것이 없다.

**설정값과 그 근거.**

| 설정 | 값 | 근거 |
|---|---|---|
| 릴레이 주기 | 30초 | 평상시 빈 결과라 짧을 이유가 없다. GUARANTEED 타입은 초 단위 지연이 무해 |
| grace (릴레이가 집지 않는 최근 구간) | 90초 | 즉시 전송의 실패 판정이 max.block.ms 60초(IN-2 실측)이므로 그보다 길게. 둘이 같은 행을 보내는 중복을 줄인다 |
| 첫 실패에서 회차 중단 | 예 | 브로커에 못 붙으면 send가 60초까지 막힌다. 200건을 순서대로 시도하면 락 최대 시간을 넘겨 다른 파드가 겹쳐 뛴다 |
| lockAtMostFor | 3분 | 최대 실행 시간(첫 실패까지 약 60초 + 성공분)보다 길게 |
| 최대 시도 | 20회 | 넘기면 DEAD로 내려 릴레이가 더 집지 않고 운영자가 본다. 무한 재시도로 백로그를 막지 않기 위해 |
| SENT 보존 | 7일 | 토픽 보존 기간과 맞춤. 매일 04:30 삭제 |

### 7.3 감수하는 비용

- at-least-once. 즉시 전송이 ack를 받았는데 SENT 갱신 전에 파드가 죽으면 릴레이가 한 번 더 보낸다.
  중복은 소비자(chat-service) 멱등으로 흡수해야 하며, 이 변경에는 포함되지 않았다.
- outbox 테이블 하나가 운영 대상이 된다. DEAD 행 수를 정리 배치가 로그로 남긴다.
- GUARANTEED 요청 경로(승인 요청)에 INSERT 1건이 붙는다. 좋아요·댓글 경로는 무변경.

### 7.4 이번에 하지 않은 것

- **`TB_BATTLE_NOTIFICATION_SENT` 흡수.** §5에서 outbox 유니크 키로 대체할 수 있다고 썼지만 이번 변경에서는
  그대로 두었다. 스케줄러의 dedup 로직과 테스트 16개를 함께 바꾸는 범위가 되어 한 번에 검증할 변경이 아니다.
  현재는 sent 테이블이 "보내기로 했다", outbox가 "전송됐다"를 각각 들고 있어 §2.2의 "실패해도 sent로 남는"
  구멍은 outbox 쪽 재시도로 닫혔다. 두 테이블을 하나로 합치는 것은 다음 회차.
- **소비자 멱등.** toy-chat 변경. clientMessageId·seq 정본화와 같은 회차 경계.

## 10. 꼬리질문 방어

- **"그냥 다 outbox로 하면 되지 않나요."**
  등급은 타입 속성이라 값 하나 바꾸면 전부 outbox다. 안 한 이유는 비용이 아니라 유실 허용 타입에서 중복·지연이
  순손실이기 때문이다. 그리고 (b)/(c) 비교를 §8로 설계해 두었고, 차이가 없으면 다 켠다.
- **"outbox면 100% 보장인가요."**
  아니다. 우리 서비스 안에서 사라지지 않는다는 보장이다. 브로커는 복제 1이라 별개 문제고, 소비자 중복은 멱등 처리가 담당한다.
- **"릴레이를 한 대만 돌려도 됩니까."**
  릴레이에 들어오는 것은 GUARANTEED 7타입뿐이고 최다 발생 타입인 좋아요·댓글은 빠져 있다. 평상시 즉시 전송이
  성공하므로 릴레이 결과는 비어 있고, 일하는 것은 복구 구간에 쌓인 "장애 시간 동안의 배틀 결과·승인 요청" 수만큼이다.
  처리량이 병목으로 실측되면 userId 해시 샤드로 리더를 늘린다. 지금은 측정된 것이 없어 "작다"가 아니라 "작을 것"이라고 쓴다.
- **"즉시 전송과 릴레이가 같은 행을 두 번 보내지 않나요."**
  보낼 수 있다. 그래서 grace를 즉시 전송의 실패 판정 시간(max.block.ms 60초)보다 긴 90초로 두어 겹침을 줄였고,
  남는 중복은 at-least-once의 대가로 소비자 멱등이 받는다.
- **"비용을 재 봤나요."**
  아직 아니다. 어디서 생기고 어떻게 재는지(§8)는 정해져 있고, 이 DB의 IOPS 고갈 이력 때문에 쓰기 축이 가장 무겁다고 본다.
  재기 전에는 "작을 것"이라고만 쓴다.
- **"기존 sent 테이블은 왜 아직 있나요."**
  outbox 유니크 키로 대체할 수 있지만 스케줄러 dedup과 테스트 16개를 함께 바꾸는 범위라 이번 변경에서 분리했다(§7.4).
  지금은 sent가 "보내기로 했다", outbox가 "전송됐다"를 각각 들고 있고, 실패한 발송은 outbox 쪽에서 재시도된다.
- **"outbox 없이 스케줄러가 안 보낸 걸 다시 찾으면 되지 않나요."**
  배틀 3종만 보면 그게 더 싸고, §6의 10번에 그렇게 적었다. 안 고른 이유는 승인 요청·초대·시스템이 요청 경로라
  타입마다 재도출 쿼리를 따로 써야 하기 때문이다. 불가 타입이 배틀 밖에 하나라도 있으면 한 테이블이 낫다.
- **"CDC는요."**
  2 replica에 Kafka Connect를 올리는 비용이 얻는 것보다 크다. 인스턴스가 수십 대가 되고 폴링 부하가 실측되면 그때 카드다.
