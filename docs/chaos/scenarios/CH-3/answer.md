# CH-3 — Mongo 짧은 다운 → 드라이버 대기 중 복구 → 지연 흡수

> Then. Given/When은 [RUNBOOK.md](../../RUNBOOK.md) §6 CH-3. 여기엔 실행 결과를 남긴다.

- **주입**: `docker stop $MONGO_CT` (infra 노드) — **다운 20~25초** (`CH3_DOWN_SECONDS`)
- **hop**: 2
- **실행 일시(UTC)**: `evidence/timeline.log`

> 분리 근거와 설계는 rca-agent [`docs/ch-3/README.md`](../../../../../yogurtte-rca-agent/docs/ch-3/README.md).

## 정답지 (원인 1줄)

Mongo 미가용 구간이 컨슈머의 첫 Mongo 작업과 겹쳤고, **드라이버 서버 셀렉션 대기(상한 30초)
안에 Mongo가 복구되어 그 첫 시도가 예외 없이 성공**했다 → 알림은 **지연 도착, 유실 0**.
재시도(`FixedBackOff` 3회)·DLQ는 **발동하지 않는다** — 예외 자체가 없기 때문이다.

## 근거 시그널 도달 경로

핵심: 댓글 API는 **200**, 알림도 **도착**한다. **에러 span이 하나도 없다.**
유일한 신호는 chat `process-notification` span 안의 **자식으로 설명되지 않는 공백**이다.

1. `process-notification` 총 시간 − 자식 span 합 = 공백 (자식들은 타임라인 **오른쪽 끝**에 몰림)
2. 그 공백이 **첫 Mongo 작업 직전**에 위치 → 드라이버 대기
3. 업스트림(content POST, `notification-publish`, `publish user.notifications`) 정상 → 발행측 무결

**CH-1과의 구별은 span 개수로 관측된다**: 이 갈래는 `process-notification` **1개**,
CH-1(경계 밖)은 `receive` **4개** + `STATUS_CODE_ERROR` + `publish …dlq`.

## 질문 (블라인드 조사 입력)

```
알림이 늦게 왔다는 제보가 있다. 원인을 조사해줘
```

**질문 문구가 이 문항의 절반이다.** 같은 트레이스라도 "알림이 **안** 왔어요"(CH-1·IN-2)와
"알림이 **늦게** 왔어요"(CH-3)는 정답이 다르다. 원인 힌트를 넣지 않는다("Mongo가 느렸나?"는 오염).

### 앵커에서 의도적으로 뺀 것 (체크리스트 근거)

- **초 수를 요건에 박지 않는다.** 공백 길이는 `CH3_DOWN_SECONDS`에 따라 달라진다.
  "드라이버 대기 상한(30초) **안쪽**"이라는 **관계**로만 쓴다.
- **Loki 로그 요건 없음.** 셀렉터 결함(`{app=~...}`)으로 6회 연속 0건 — 에이전트 **채널 밖**이다(유형 B 회피).
- **baseline 대조 요건 없음.** v0 입력은 traceId 1개뿐 — AU-4에서 이 실수로 −10점을 매겼다.
- **복구 권고를 조치 만점 요건에 넣지 않는다.** 지연 흡수 문항이라 **조사 시점에 이미 복구가
  끝나 있다.** CH-2 회차1에서 "복구를 권고할 수 없는 시점"이 채점 불가를 만든 결함 ⑥의 반복을 막는다.
- **오판(10)과 미판단(20)을 분리**했다 (결함 ③), 근본 원인에 **중간 구간 30**을 뒀다 (결함 ②).
