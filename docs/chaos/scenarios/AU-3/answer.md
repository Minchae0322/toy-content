# AU-3 — JWT 시크릿 드리프트 (config drift)

> Then. Given/When은 [RUNBOOK.md](../../RUNBOOK.md) §6 AU-3. 여기엔 실행 결과를 남긴다.

- **주입**: secret `JWT_SECRET` 변경 + content rollout restart
- **hop**: 1
- **실행 일시(UTC)**: `evidence/timeline.log`

## 정답지 (원인 1줄)

content의 JWT_SECRET이 auth와 어긋남(config drift). 로그인은 되는데 아무것도 안 되는 상태.

## 근거 시그널 도달 경로

핵심: **401은 4xx라 span에 error 태그가 안 붙는다.** 자동 탐지(`status=error` 검색)로는 안
걸린다 — 그러나 **"trace로 못 찾는다"는 뜻이 아니다.** 트레이스에는 상태와 필터체인 구조가
남는다(v2 정정, 아래).

1. trace — `status` 속성 값 + Spring Security 필터체인 span의 **중단 지점**
2. Loki — `{service_name="content-service"} |= "JwtFilter"`
3. Mimir — 401 rate 급증

## 채점 앵커 — **v2 (2026-07-28 개정 · 회차 1부터 적용)**

> **v1 정정 사유**: v1은 *"trace로는 못 찾는 문항"*을 전제로 만점 요건을 메트릭·로그에만
> 걸었다. 그러나 실측 확인 결과 트레이스에 **`status` 속성**(정상 요청에서 `"status":"200"`
> 확인)과 **Spring Security 필터체인 span**(`security filterchain before/after`,
> `secured request`, `before *Filter` 다수)이 존재한다. 401이면 필터체인이 중단되고
> `secured request`·컨트롤러·DB span이 사라질 것이므로 **부재 신호로 도달 가능**하다.
> v1대로 두면 CH-2와 같은 실패(요구 신호가 수집 범위 밖 → 채점 불가)가 난다.
>

**설계 의도 — 신호 목록이 아니라 배제 논증으로 잰다.**

이 문항은 어느 한 채널도 단독으로 답을 주지 않는다. trace는 **401이라는 사실**만 주고 *왜*를
말하지 않는다. 로그는 **검증 실패 지점**을 주지만 *범위*를 말하지 않는다. 401 rate는 **범위**를
주지만 *원인*을 말하지 않는다. 그래서 요건을 "무엇을 봤는가"가 아니라 **"무엇을 배제했는가"**로
쓴다 — ⓐⓑⓒ가 각각 하나의 경쟁 가설을 죽이고, 셋이 죽으면 남는 것이 config drift다.

| 요건 | 죽이는 가설 | 채널 |
|---|---|---|
| ⓐ 필터 단계에서 끊김 | **앱 버그** (컨트롤러가 500을 냈다) | trace |
| ⓑ 실패 사유가 서명/키 불일치 | **토큰 만료** ← **이 문항의 핵심 함정** | Loki |
| ⓒ 전역 급증 | **개별 요청·사용자 문제** | Mimir |

**ⓑ가 결정적이다.** 증상(401 급증)만으로는 만료와 구별되지 않고, v0 에이전트는 **재로그인
실험을 할 수 없다**(traceId 1개만 받는다). 관측으로 가를 수 있는 유일한 지점이 **로그에 남는
실패 사유**다 — AP-1(`Data too long`)과 AP-3(`Duplicate entry`)를 같은 예외의 *지문*으로 가른
것과 같은 구조다.

> **ⓑ의 구체 문언은 검증 후 확정한다.** 실제 로그가 `SignatureException` 계열인지,
> 어떤 메시지로 찍히는지 **아직 실측하지 않았다.** 예외 클래스명을 지금 박으면 AU-4를
> 채점 불가로 만든 **유형 C**(코드 독해를 실측으로 착각)의 재발이다. 아래 체크리스트에서
> 확인한 문언으로 교체한 뒤 주입한다.

**이중 감점 방지**: ⓑ 미충족이 3) 오귀인 감점으로도 이어지려면 **만료라고 확정**해야 한다.
사유를 확인하지 못했을 뿐이면 근거 경로에서만 감점하고 오귀인은 만점을 유지한다
(AP-2 선례 — "가능성으로 남기는 것과 확정하는 것은 다르다").

세 채널 모두 **수집 범위 안**이다(Loki = B-1·B-2, 401 rate = B-3 보강). 도구 제약으로 인한
상한이 없으므로 **못 엮으면 그대로 감점**이다.

**핵심 함정은 "토큰 만료"다.** 증상(401 급증)이 만료와 구별되지 않으므로, **재로그인해도
그대로 401**이라는 점을 짚어야 드리프트에 도달한다. 그래서 오판을 10점 구간에 따로 뒀다
(오판은 미판단보다 무겁다 — 결함 ③).

### 박제 전 검증 체크리스트 — **주입 없이 할 수 있다**

AU-3 주입은 **전 사용자 401**이라 부담이 크지만, **앵커 검증용 401은 무해하게 만들 수 있다** —
잘못된 Bearer 토큰으로 인증 API를 한 번 호출하면 된다. 그 트레이스로 ⓐⓑ를 확인한다.

```bash
# 정상 대조
TOKEN=$(curl -s -X POST $BASE/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"'$EMAIL'","password":"'$PASSWORD'"}' | jq -r '.accessToken')
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/content/feeds/following" -H "Authorization: Bearer $TOKEN"

# 401 트레이스 생성 (인프라 무접촉)
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/content/feeds/following" -H "Authorization: Bearer not-a-valid-token"
```

- [ ] 401 트레이스에 **`status` 속성이 `"401"`로** 찍히는가
- [ ] 필터체인이 **어느 span에서 끊기는가** — 이름을 그대로 기록해 앵커 ⓑ 문언에 반영
- [ ] `secured request` span이 **사라지는가**
- [ ] 컨트롤러·서비스·DB span이 **전무한가**
- [ ] `{service_name="content-service"} |= "JwtFilter"` 로그가 **실제로 잡히는가** + **레벨**은
      (ERROR/WARN이 아니면 rca-agent의 `errorWarnQuery`로는 못 잡고 `traceIdQuery`에만 의존한다)
- [ ] **⭐ 실패 사유가 로그에 남는가** — 서명 불일치와 만료가 **다른 문구**로 찍히는가.
      만료 토큰으로도 한 번 호출해 **두 로그를 나란히 확보**한 뒤, 그 문언으로 ⓑ를 확정한다.
      **둘이 구별되지 않으면 ⓑ는 성립하지 않으므로 요건에서 빼고** 만료 배제 경로를 다시 설계한다
- [ ] 평시 401 rate 기준선 기록 ("급증" 판정의 대조군)
- [ ] 401 rate 쿼리가 **실제로 시리즈를 반환하는가** —
      `sum(rate(http_server_requests_seconds_count{application="content-service", status="401"}[1m]))`.
      빈 값이면 ⓒ가 달성 불가이므로 요건에서 빼거나 지표를 먼저 확보한다
- [x] **수집 창 안에 평시 구간이 있는가** — **하네스로 해소(2026-07-28)**. rca-agent의 창은
      **트레이스 span ±120초(≈4분)**라, 주입 후에만 트래픽이 있으면 창 전체가 이미 401 상태여서
      "평시 대비 급증"을 볼 수 없다. `inject_AU_3`가 **주입 전에 평시 트래픽 60초**를 흘리고,
      `trigger_AU_3`가 주입 후 **90초간 401을 쏜다.** 조사 입력은 fire 구간 **중반**의 traceId를 써서
      창에 양쪽이 들어오게 한다. **warm 구간에 401이 섞이면 그 회차는 대조군 오염**이다

### 왜 traceId가 필요한가 — 이 문항이 v0 입력 모델의 한계를 드러낸다

**rca-agent는 traceId가 없으면 조사 자체를 못 한다.** `RcaController`의 요청 record가
`@NotBlank String traceId`이고, 더 근본적으로 **Loki·Mimir의 조회 시간창이 트레이스에서
파생된다** — `Collector`가 `TimeWindow.fromTrace(traceJson, padding)`으로 창을 만들고
그 창으로 로그·메트릭을 조회한다. traceId는 조사 *대상*이라기보다 **시간 앵커**다.

**그런데 AU-3는 전역 장애다.** 특정 요청이 아니라 *모든 사용자의 모든 인증 API*가 401이고,
앵커 ⓒ가 요구하는 것도 "**401 rate가 전역 급증**"이라는 집합적 사실이다.
**요청 1건에 앵커를 거는 입력 모델과 어긋난다** — 하네스가 평시 트래픽을 앞에 깔고
traceId를 골라주는 것도 이 어긋남을 우회하기 위한 것이다.

> **채점에 미치는 영향은 없다.** 에이전트는 주어진 창 안의 메트릭 시계열을 그대로 받으므로
> ⓒ 판정은 성립한다. 다만 **"장애를 어떻게 지목해서 조사를 시작하는가"가 v0에서 해결되지
> 않았다**는 사실은 기록해 둔다 — 실무에서는 traceId가 아니라 알람·시간대로 조사가 시작된다.
> [B-4](../../../../../yogurtte-rca-agent/docs/round-2/README.md)(수집 창)와 같은 뿌리다.

### 하네스가 대신 하는 것 (2026-07-28 신설)

`./chaos.sh AU-3 run`이 위 체크리스트의 기계적인 부분을 수행한다.

| 문제 | 하네스 처리 |
|---|---|
| **401이 1건이라 rate 급증이 안 생김** | `trigger_AU_3` — 초당 1회 × 90초. 구 런북은 트리거가 `measure` 안에 **1회**뿐이었다 |
| **traceId를 건질 수 없음** | `traceparent`를 직접 주입해 **traceId를 사전 확정**. 401은 `status=error`가 아니라 Tempo 기본 검색에 안 걸리고 `http_code`는 상태 코드만 준다 |
| **평시 대조군 부재** | `inject_AU_3`가 patch 전에 평시 트래픽 60초 선행 |
| **ⓑ 검증 시점** | baseline 게이트에서 **서명 훼손 토큰**으로 1회 호출해 실패 문구를 미리 확보 |

**게이트 2개가 baseline에서 먼저 돈다.** ① traceparent가 채택되는가(안 되면 전파가 W3C가
아니라는 뜻이고 조사 입력을 못 만든다) ② 서명 실패 로그 문구가 무엇인가(만료와 구별 안 되면
**ⓑ를 요건에서 뺀다**). 둘 다 **주입 없이** 확인된다.

> 요건이 실제와 어긋나 채점 불가가 난 것이 [유형 C](../../../../../yogurtte-rca-agent/docs/scoring/README.md)(AU-4)다.
